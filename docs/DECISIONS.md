## 2026-10-25 · Approve pauses the graph; Postgres checkpointer on the direct endpoint
- Decision: the agent graph now runs propose → approve → execute → verify. A proposal with no auto-approval pauses at `approve` with LangGraph `interrupt()`; the state is checkpointed with `langgraph-checkpoint-postgres` in schema `lg` on thread `<tenant_id>:<case_id>`. `POST /approvals/{id}/decision` queues `after_decision`, which resumes that thread with `Command(resume=...)`, in any process. The approve node reads the decision from the database (bound to the payload hash), never from the resume value, and has no side effects, because a resumed node re-runs from its start. Cases with no paused thread (the deterministic path, or a checkpointer that can't be reached) go straight to the code path: execute, then verify. Both paths are idempotent (stable key, final verdicts). A customer reply on an `awaiting_info` case (POST /cases on the same order) resumes the `wait_info` interrupt with the reply. A resume claims the paused `workflow_runs` row under the case lock, so a double reply continues the thread once.
- Checkpointer connection: its own short-lived psycopg connection per run or resume, as the same app role (NOBYPASSRLS), on the direct endpoint (the engine's host without `-pooler`), with `search_path=lg`, autocommit, and `setup()` on first use (the role already has USAGE+CREATE on `lg` from neon_bootstrap.sql, so no migration).
- Why: Neon's pooler is PgBouncer in transaction mode. It rejects the `search_path` startup option (tested), and session state isn't safe there. Autocommit keeps every checkpoint write a short transaction of its own, so nothing is open during an LLM or provider call (rule 5). The library's tables have no tenant_id or RLS, so isolation comes from the thread id. It is built only from the auth/system tenant and a case loaded under that tenant's RLS, and no API takes a thread id as input.
- Exception to hard rule 1 (needs the human's sign-off): the `lg` tables hold case state, including the customer's message text, with no RLS. Any SQL run as the app role can read every tenant's checkpoints. Ways to close it later: keep only ids in the graph state and reload text from RLS tables, or give the checkpointer a separate role that only it uses.
- Review fixes: an approved decision whose resume is refused for any reason (for example, the first pass hasn't marked its run `paused` yet) falls back to the idempotent code path. A failure after a resume claimed the run escalates the case rather than dropping the reply. The verifier locks the execution row, so overlapping passes record one final verdict. "No approval yet" at execute time waits instead of escalating. A failed refund is shown as "needs a check" until the verifier confirms the failure.
- Alternative rejected: the owner role from MIGRATION_DATABASE_URL for the checkpointer (runtime would hold owner credentials); the pooled endpoint with schema-qualified names (the library's SQL is unqualified); a separate CHECKPOINT_DATABASE_URL setting (one more secret to keep in sync; can be added later if a non-Neon pooler needs it); running every case through the graph, deterministic ones included (the no-LLM path must stay runnable on its own).

## 2026-10-26 · `lg` checkpoint schema: exception to rule 1, signed off, with four guards
- Decision: the LangGraph checkpoint tables in schema `lg` have no `tenant_id`/RLS (the library owns them). The human signed this exception off on 2026-10-26 on condition of these guards, all implemented and tested in `tests/integration/test_workflow_resume.py`.
- Guard 1, ids only: graph state holds tenant_id, case_id, run_id, proposal_id, category code, need code, outcome/approval/execution codes and the step count. The customer message, evidence, policy text, draft and model reasons live in `Deps.scratch` (in-process, per run, never checkpointed). A resume re-reads what it needs from the database under the tenant's RLS session: the customer's words come from the ticket messages (the reply is saved there before the resume, so the resume value is just `{"kind": "info"}`). A test greps every `lg` row of a run for a distinctive message, the model's reason, policy text and order items.
- Guard 2, ownership: `resume_case` first loads the case in `tenant_session(tenant)` (not found means refuse), then refuses when the stored thread's tenant_id or case_id differ from the caller's. Tests: a thread copied under another tenant's id, and a thread whose stored tenant was altered.
- Guard 3: no route reads or takes a thread id; a test scans the route table.
- Guard 4, prune: a finished run (not paused) deletes its thread; `prune_finished(engine, tenant_id)` is the sweeper entry for what that missed (crash between finish and prune). Paused threads are kept.
- Why: checkpoints are a second copy of case data outside RLS; keeping them to ids makes a leak worthless and a stale copy harmless, and the database stays the one source of truth.
- Alternative rejected: encrypting full state (key handling for little gain); adding tenant_id/RLS to library tables (breaks on library upgrades).
- Shared helpers and the baseline: `gather_evidence`, `retrieve_policies`, `store_proposal`, `ask_customer`, `escalate_case` read and write `Deps.scratch`, not graph state, so the one-call baseline (`build_baseline_graph(deps, checkpointer)`, passed to `run_case(..., build=...)`) keeps text out of checkpoints too. Both pipelines run through the same checkpointed `run_case`, so a finished eval run prunes its thread like any other.
- Trade-off: if a process dies mid-invocation, the restarted run lacks the scratch data (evidence, draft). The node that needs it fails and the case escalates to a person, never guessing. Only the pauses (approve, wait for reply) are resumed across processes, and they need ids only.

## 2026-10-25 · Verifier gates "confirmed"; domain events drive customer updates
- Decision: after execution, the verifier re-reads the provider by idempotency key and compares status, amount and provider reference with our execution. It records a `verifications` row (verified / mismatch / unknown). A case becomes `resolved` (customer stage "confirmed") only on a verified success. A mismatch, or a confirmed failure, escalates. A verdict of verified or mismatch is final and isn't fetched again. `RefundOutcome` gained `amount_paise` so the verifier can check the amount. Case transitions emit domain events (`case.opened/proposed/approved/rejected/executed/verified/escalated/awaiting_info`) into the `domain_events` outbox in the same transaction. In-process subscribers run inside a savepoint, and `publish_pending` retries any that failed. The first subscriber (app/modules/support/customer_updates.py) posts `case_status`'s code-templated message on the case's ticket and moves the ticket status. It skips a message identical to the last one, so it is idempotent. A rejection closes the case (stage "declined"). An approval that expires before execution escalates without sending anything.
- Why: the executor records what the provider answered at call time, and the verifier checks that the provider still agrees, so "confirmed" means two reads agree (rule 7). Building the message from `case_status` at event time means the ticket can never say more than `GET /cases` does. A subscriber failure doesn't roll back the state change.
- Alternative rejected: confirming on the executor's answer alone (a single read); subscribers after commit with no outbox (an update is lost if the process dies); a separate message template per event (two sources of truth for customer text).
- Open: subscribers are in-process only, and nothing runs `publish_pending` on a schedule yet. That fits with the E4.5 sweeper.

## 2026-10-26 · Evals: selectors, rule-derived ceilings, deterministic scoring, one-call baseline
- Decision: scenarios live in `tenants/<slug>/scenarios/*.yaml`, one per file, validated against the tenant's pack. Each names an order *selector* (`most_late`, `late_between`, `on_time`, `shortfall`, `flagged`, `latest`, `none`), never an id, so they survive a reseed. A selector may add `placed_on`: the harness moves the picked order (and its fulfilment and payments, intervals kept) to that business date, because the generated history ends before rules dated later (e.g. late_delivery_v4's 25% tier from 2026-10-26). `make eval` reseeds (SEED=42, scale 0.25 by default), opens a free-text case per scenario directly in the DB, runs `run_agents` (real LLMs), and reads the result back from the DB. The amount check compares the proposal with `decide_remedy` for the *expected* category: scoring never uses model output except as the thing measured. The single-agent baseline (`app/engine/baseline.py`) does one LLM call (classify + propose) with the same tools, retrieval, ceiling, `_check_draft` and `store_proposal`. It gets every category's ceiling up front, since the category isn't known before the call, and gets no repair round. The `pytest -m live -k proposal` check reuses the harness on the test DB with the 3 `live`-tagged scenarios per tenant. Costs are list-price assumptions in integer paise per million tokens, priced at the main model's rate. `get_settings` honours `ENV_FILE` for the dotenv path, so a second checkout can reuse the main one's keys without copying them.
- Why: hard-coded ids break on every reseed. A rule-derived ceiling keeps "within ceiling" independent of what the model claimed. Opening cases in the DB rather than through the HTTP API keeps eval latency about the pipeline, and the API path is already covered by `make flight`. A baseline that shares every check isolates what splitting into specialists buys (one prompt against two), not differences in guard code.
- Alternative rejected: an LLM judge for outcomes (spec: a judge may score wording only, never whether money moved); a baseline with its own looser checks (the comparison would measure the guards, not the agent design); eval cases through `POST /cases` (needs a demo login per customer; most history customers have none).

## 2026-10-25 · Operator release of quarantined refunds waits out the provider's request lifetime
- Decision: `POST /approvals/{id}/release` (hq_owner only) frees a refund held as `pending_reconciliation`, or `reserved` and never confirmed. The request checks, from the DB only, that the row is still held, that its approval can no longer be executed (otherwise the sweeper should finish it), and that the window has passed. The window is the later of the ledger's last change and the approval's expiry, plus the payment connector's `request_lifetime`, plus a 5-minute margin. Workers only send while the approval is usable, so the approval's expiry bounds the last send. A background task then asks the provider by key. If the provider has the refund, it is recorded and never freed. If not, the ledger moves to a new status, `released` (migration 0014), by compare-and-set on the status seen, and the execution becomes `failed` with the error "released by operator". The release is audited with the operator's user id. The mock provider now models late landings: a timed-out request may still be applied up to `request_lifetime_s` after it was sent, and never after that.
- Why: "the provider has no record yet" is not proof while a request may still be in flight. The provider's request lifetime is what turns it into proof. `released` stays distinct from `failed` (the provider declined), as rule 7 requires. The compare-and-set means a late landing recorded by a concurrent reconcile wins over the release.
- Residual risk (accepted): the window assumes the provider honours its lifetime, and that no worker stalls for longer than the margin between its usability check and its send.
- Alternative rejected: releasing on the first "no record" (could double-pay); releasing to `failed` (it would merge two different facts); a per-send `last_sent_at` column (adds a write before every send, and still can't see a stall after the write).

## 2026-10-25 · A sweeper finishes approved work and escalates dead agent runs
- Decision: `app/engine/sweeper.py` (`make sweep`) runs per tenant, under RLS, for every tenant folder. It does three things. (1) It executes approved, unexpired proposals that have no execution, through the same executor and stable key. (2) It reconciles executions left `submitted`/`unknown`/`processing` by key; this also records a quarantined refund's late landing. (3) It escalates cases stuck in `investigating` whose agent run died or never started, and marks the dead run failed. Fresh work (under 1 minute old) is left to its background task. The agent's propose step now locks the case and adds nothing if the case is no longer `investigating`, so a run that outlives its TTL can't add a proposal after the sweeper escalated the case. The sweeper does not run on API startup; it is a cron-style command.
- Why: in-process background tasks die with the process. The executors already serialise on the proposal and resume by key, so a sweep racing a live task still writes once. Escalating instead of re-running keeps a maintenance job from spending LLM budget, and a person sees the case at once.
- Alternative rejected: re-running the agent graph from the sweeper (it costs LLM budget, and the customer's message would need replaying); an external queue (Celery/RQ) for v1 (more infrastructure for the same guarantee).

## 2026-10-25 · Vouchers are executed like refunds, through a voucher connector
- Decision: an approved `free_item_voucher` (auto-approved on either path, or approved by staff) is issued by `app/engine/voucher_executor.py` through a `vouchers` connector chosen by the `vouchers_connector` setting (mock: `mock_vouchers`). It follows the refund recipe: a short transaction inserts the execution under the stable key `P-<proposal_id>:voucher:1`, the provider is called outside any transaction, status writes only move forward, and a resume asks the provider by key before sending again. There is no money ledger, because a voucher holds no refundable balance. The customer reference comes from the case row, never from params. The case becomes `resolved` only when the provider confirms the voucher (`escalated` if it declines), and `case_status` says "issued" only then. `app/engine/dispatch.py` maps each action to its executor. The deterministic path and staff approvals queue it as a background task after commit; the agent path runs it after the graph run is recorded.
- Why: E4.6. An auto-approved voucher used to sit in `executing` with nothing issuing it. Reusing the refund recipe gives the same exactly-once guarantees.
- Alternative rejected: issuing vouchers inside the decision transaction (a network call inside a transaction, rule 5); treating approval as issuance (rule 7).

## 2026-10-26 · Fair-use signal (E2.5): count approvals, block auto-approve only
- Decision: the fair-use count is the number of refund or voucher proposals *approved* (by a person or a tenant rule) for the case's customer in the 30 days before now; rejected ones and ones older than 30 days don't count. Which actions count is a flag on the action (`counts_as_grant`: refund, free_item_voucher), not a list in core code. `fair_use_max_grants_30d` is a `kind: limit` pack setting (default 3, lowerable only). `evaluate_proposal` adds `fair_use_ok`, `fair_use_grants_30d` and `fair_use_max_grants_30d` to the checks of every counting proposal; `auto_decide` (used by both the deterministic and the agent path) returns None when `fair_use_ok` is false and audits `approval.auto_skipped`. It never changes `ok` or `errors`, so the proposal stays eligible and pending: a person decides, and the approvals list shows the count.
- Why: vouchers have no executor yet, so "executions succeeded" would never count them; the approval is the grant decision. Counting approved-but-later-failed or expired refunds over-counts, which only sends more cases to a person (the safe direction for a signal that never denies). The customer id comes from the case record and RLS confines the count to the tenant.
- Alternative rejected: counting succeeded executions (misses vouchers); counting opened cases, as the old fair_use_v1 prose said (punishes customers for our mistakes; the policy text now says "granted"); making fair use an eligibility error (that would be an automatic denial).

## 2026-10-26 · Graduated late tiers (E3.5): dated tiers in settings, exclusions from delivery records
- Decision: settings are not date-versioned (tenant_settings has one value per key and scope). Instead, a `late_delivery_tiers` entry may carry `effective_from` / `effective_to` (quoted ISO dates, `to` exclusive), and the resolver picks the highest tier reached among those in force on the *order date* (`placed_at`), the same rule policy retrieval uses. Spice Route's org settings hold the v3 tier (45+ min: 50%, until 2026-10-26) and the v4 tiers (20: voucher; 45: 25%; 60: 50%, from 2026-10-26); `late_delivery_v3` gets `effective_to: 2026-10-26` and `late_delivery_v4` starts that day. Percent tiers stay requests capped by `refund_max_percent`. Boundaries are whole minutes, so the policy prose reads "60 minutes late or more", "45 to 59", "20 to 44" to match the code exactly. Customer-caused delays: `late_delivery_excluded_causes` (pack value, default `[customer_address_error, customer_unreachable]`) is matched against `fulfilments.attributes.delay_cause` from the delivery record; a match gives no remedy (outcome apology), never from the customer's text. Unit tests tie the prose percents to the tiers in force on each policy version's start date.
- Why: the safest behaviour is that a tier change never re-prices orders placed under the old policy (v4 lowers 45 to 59 minutes from 50% to 25%), and the customer's cited policy and the amount must agree.
- Limitation: other settings (caps, vouchers) still apply as of now, not as of the order date; and the v2 era (orders before 2026-09-01) is not encoded in tiers, so such orders are judged by the v3 tiers, as before this change. The order date is `placed_at`'s date as stored (UTC), as in retrieval. No mock or simulator writes `delay_cause` yet, so the exclusion only fires when a connector records it.
- Alternative rejected: date-versioning the tenant_settings table (a migration and a resolver change for one setting); applying v4 tiers to all orders (underpays orders placed under v3).

## 2026-10-26 · Policy wording (E3.5): edited in place where remedies didn't change
- Decision: payments_v1 (both tenants) cites the bank's timeline "per RBI turnaround-time rules" without quoting days, adds a debited-but-not-confirmed clause (tell only what the provider confirmed, never promise the bank's compensation); refunds policies (both) add an aggregator clause (aggregator orders: the app refunds; we offer a voucher or escalate); BrewCo order_accuracy_v2, quality_v1 and refunds_v1 state remake-or-voucher first, refund second; fair_use_v1 (both) says "granted three or more refunds or vouchers". These are edited in place; only late delivery got a new version. The voucher auto-approve cap was already a `kind: limit` pack default of 15000 paise in both packs (verified, unchanged); a unit test now pins it.
- Why: these are wording clarifications of rules code already applies, so a new version would only duplicate text; late delivery changes amounts, so it is versioned for the order-date rule.
- Alternative rejected: new versions of every edited policy (churn with no change in outcome).

## 2026-10-26 · Product decisions from the market research (human)
- Decision: (1) Spice Route late delivery uses graduated tiers: a voucher for 20 to 45 min late, 25% for 45 to 60 min, 50% for over 60 min, nothing for customer-caused delays, and all values in tenant settings. (2) A fair-use check: when a customer was granted 3 or more refunds or vouchers in the last 30 days, the next case is never auto-approved and goes to a person. ## 2026-10-25 · Web app structure: one API client, display-only stage map, manuals bundled from docs
- Decision: `web/src` is split by layer: `api/` (one `request()` that adds the bearer token, parses `{detail}` errors into `ApiError`, and reports a 401 so the session ends), `auth/` (token in memory + `sessionStorage`, identity from `GET /me`), `pages/` per screen, `components/`, and `lib/` for pure display helpers (paise → ₹ with integer maths and en-IN grouping, stage → label/colour/stepper position, role → nav). Data fetching is a small `useApi` hook plus `usePolling` (3 s, stops after 2 min); no global store or query library. Contract fields marked NEW are optional types and the UI hides what's absent. The Help page imports `docs/manual/*.md` at build time (`?raw`) and renders them with `marked` + DOMPurify. Dependencies are pinned exactly; Vite 6 / Vitest 3 because the 5/2 lines had high/critical dev-server and test-runner advisories.
- Why: one client means one place for auth headers and 401 handling, which the tests cover. Keeping stage meaning as a display map (the API decides the stage, `message` is the customer text) honours "no business rules in the UI". Markdown in docs/manual is one source for repo readers and the in-app Help, so they can't drift; sanitising keeps it safe if the content ever stops being ours.
- Alternative rejected: TanStack Query/Redux (more moving parts than ~10 screens need); manuals written as TSX (two copies, or docs unreadable on GitHub); computing remedies, limits or eligibility in the UI (Approve is disabled only from the API's `eligible` flag; 403/409 come from the API).

## 2026-10-25 · Login lockout counters in a tenant-owned table
- Decision: failed logins go into `login_failures` (migration 0013). It has `tenant_id` and RLS like every tenant table. Each row stores a sha256 of the normalised email (trimmed, lower-case) and `failed_at`. If a tenant+email has 5 failures in the last 15 minutes (settings `LOGIN_MAX_FAILURES`, `LOGIN_WINDOW_MINUTES`), the next login gets 429, even with the right password. A successful login deletes that key's rows. Each failure also prunes every expired row of the tenant, so one-off emails can't grow the table. Unknown emails are counted the same way, so a 429 doesn't reveal whether an account exists. Failures against a tenant slug that doesn't exist aren't stored, because there's no organization row for the FK. That's fine: `/auth/businesses` already lists the tenants. The app role may select, insert and delete these rows, but not update them.
- Why: a DB table survives restarts and works across several API workers. Making it tenant-owned keeps hard rule 1, and the existing RLS isolation tests cover it automatically. Hashing the email means arbitrary strings typed by attackers are never stored.
- Alternative rejected: in-memory counters (reset on restart, separate per worker); a platform table keyed by slug + email hash (a second kind of tenant key outside RLS).
- Known gaps (accepted for now): the count and the insert are not atomic, so a burst of parallel requests can get a few extra tries past 5; an advisory lock per key would close it. Anyone who knows an email can lock that account for 15 minutes (the price of a hard lock). There is no per-IP or per-tenant throttle on bcrypt work yet; that belongs in a rate limiter in front of the API.

## 2026-10-25 · bcrypt login; DEMO_AUTH now only governs demo passwords
- Decision: `/auth/login` always checks the password against `users.password_hash` (bcrypt, cost `BCRYPT_ROUNDS` with a default of 12; tests use 4). Every attempt runs one bcrypt check. Unknown users, users without a hash and passwords over 72 bytes are checked against a dummy hash, then fail. All of these get the same 401 `invalid credentials`. The bcrypt check runs between two short transactions, so no pooled connection is held during it. The plaintext demo passwords live in the tenant folders (`demo_password` per tenant in `tenants/<slug>/tenant.yaml`, with an optional per-user override). The loader hashes them into the DB only when `DEMO_AUTH=true` and `APP_ENV` isn't prod, and clears those users' hashes otherwise. Those hashes are marked `users.password_is_demo`, and login refuses a demo hash unless demo accounts are enabled. So a dev-seeded database served in prod has no known-password logins, even before a reload clears the hashes (safety review). It keeps a hash that still matches, so reloading stays idempotent even though bcrypt salts are random. `GET /auth/demo-accounts` returns 404 in prod and also whenever `DEMO_AUTH` is off. The shared `DEMO_PASSWORD` setting is gone. Login responses now carry `expires_at`.
- Why: a real login has to work in prod, where `DEMO_AUTH` must be off. What must never exist in prod is a known password, so the flag now gates that and not login itself. Per-tenant passwords in config keep tenant names out of `app/`.
- Alternative rejected: keeping login behind `DEMO_AUTH` (prod would have no login at all); storing demo passwords in the DB or in code; truncating long passwords to 72 bytes (two different passwords would match the same hash).

## 2026-10-25 · Public business list through a SECURITY DEFINER function
- Decision: `GET /auth/businesses` reads `public_businesses()`, a SQL function owned by the migration owner with `SECURITY DEFINER` and a pinned `search_path`. It returns only slug, name and vertical pack for every organization. The app role may EXECUTE it and nothing more.
- Why: the login screen needs the list before anyone is logged in, and RLS correctly hides other tenants' rows from the app role. A narrow function exposes exactly three columns and leaves RLS untouched on everything else.
- Alternative rejected: an extra SELECT policy on `organizations` (it would break "a tenant sees only its own rows" for every query); reading the tenant folders at runtime (in prod the DB, not the folders, is the source of truth).
- Note: this relies on the owner having BYPASSRLS, which is true on Neon. Without it the function returns no rows, which fails closed. Every organization is listed. That's right for two demo tenants, but a real platform needs a "listed on the login screen" flag (or per-tenant login URLs).

## 2026-10-25 · React web frontend and email + password login
- Decision: the product UI is a React + TypeScript + Tailwind app in `web/` (built with Vite), talking only to the HTTP API through docs/api/frontend-contract.md. Login is email + password, checked against a bcrypt hash stored per user. Login failures get one uniform 401 and a lockout after 5 failures. Dev demo accounts get known passwords, which the login page lists in dev only. The Streamlit app stays as a debug UI until the React app reaches parity.
- Why: the human tested the Streamlit demo and found it too basic to follow the flow or show as a product, and chose a real web frontend. A shared demo password isn't a login. A written contract lets the backend and frontend be built in parallel.
- Alternative rejected: polished Streamlit (the human chose the React option); server-rendered Jinja/HTMX (a second web layer inside the API); self sign-up now (an abuse surface, not needed for the demo).

## 2026-10-24 · The tenant's business rule caps what the AI can propose
- Decision: in agents mode, `decide_remedy` (the deterministic rule engine) sets the ceiling for each case. The model is offered only that rule's action and may propose an amount at or below the rule's amount, or escalate. A category with no automatic rule escalates without calling the model. Policy text never raises the ceiling. A provider error that isn't a rate limit falls back to the next provider.
- Why: Flight 2 (real LLM) proposed 100% refunds at one tenant. Two were for a prompt-injection message on an order 8 minutes late, and one was for a quality complaint whose configured remedy is a voucher. The model cited a refund policy's "up to the amount paid", and code checked only the refund cap. Policy text is untrusted (rule 9), so the money decision has to come from configured rules.
- Residual risk (accepted): a customer's text can steer the classifier toward a more generous category. `decide_remedy` reads facts (line items on record, real delivery timestamps), not text, so the worst case is the auto-approve voucher for a category that doesn't fit the complaint. That is the same trust level as the customer picking a category on the form.
- Alternative rejected: letting the model set amounts within the refund cap (shown unsafe in Flight 2); a second LLM call to judge the first (it can be fooled the same way).

## 2026-10-24 · Agent case loop: code writes everything the customer sees and every proposal
- Decision: free-text cases (`ENGINE_MODE=agents`, no category) run a LangGraph graph: classify → investigate (read tools scoped to the case's customer) → policy (retrieval by order date, brand, location) → resolve (model drafts) → propose (code calls `create_proposal`). Code checks every draft before storing it: an enabled action, strict params, the case's own order, eligibility limits, and at least one citation from what retrieval returned. A rejected draft gets one repair, then the case is escalated. Clarifying questions are fixed templates chosen by code. A model answering "none" escalates for a person to confirm. A low-confidence or unknown classification asks the customer. Any exception escalates. A run claims the case under a row lock, so a resubmitted report can't start a second run. The query is embedded before the DB transaction opens. Customer and policy text are HTML-escaped inside their fences. `create_proposal` takes a tenant id rather than a role-bearing context. The deterministic path (customer picks a category) is unchanged and stays the default.
- Why: the model only chooses among options that code then verifies (hard rules 4, 7, 8, 9). Model-written customer text could promise a refund after prompt injection. A model-closed case would never be seen by a person. A background task has no caller, so an uncaught error would leave the case in "investigating" forever.
- Known gap: an auto-approved voucher puts the case in `executing`, but nothing issues the voucher yet, on either path. Refunds are never auto-approved. Tracked as E4.6. A `running` workflow run older than 10 minutes counts as dead, and the next claim takes the case over.
- Alternative rejected: an LLM-written clarification filtered by a deny-list (a deny-list can't cover every promise); auto-resolving on "none" (no human check on a decline); `with_structured_output` tool calling (JSON prompting works the same on all three providers).

## 2026-10-24 · LLM hardening: no cache in prod, secret keys, two budget caps
- Decision: settings refuse `LLM_CACHE=true` when `APP_ENV=prod` (same validator as the demo-auth/JWT rule). `GEMINI_API_KEY`/`GROQ_API_KEY` are `SecretStr`, unwrapped with `.get_secret_value()` only where `app/llm/providers.py` hands them to the SDK; settings use `hide_input_in_errors=True`. `RunBudget` has two caps: `llm_max_calls_per_run` (8) counts logical calls (each invoke, repairs and cache hits included; retries and fallbacks not) and `llm_max_provider_requests_per_run` (24) counts every request actually sent (retries and fallbacks included; cache hits send none). Either raises `BudgetExceeded`. Rate-limit detection now trusts an HTTP status attribute when present and otherwise matches phrases, never a bare "429". The UI takes identity from `GET /me` and categories from `GET /meta/categories`.
- Why: the cache writes full prompts and replies, customer text included, to local disk with no retention or tenant scoping. `SecretStr` keeps keys out of `repr`, logs and tracebacks, and pydantic otherwise echoes the bad input in a ValidationError. The logical cap keeps routing identical with and without the cache, but on its own one call could fan out to (retries+1) x providers requests; the second cap bounds that cost. "429" in text matched ports and request ids.
- Alternative rejected: one cap counting provider requests (cache on/off would change when a run escalates, so evals would differ); scrubbing keys from error text by pattern (misses formats; hiding input is total).

## 2026-10-24 · Policy retrieval: versioned, scoped, fastembed
- Decision: policies are markdown with front matter (`id, title, topic, version, effective_from, effective_to, scope`); each numbered heading is a chunk with `section_ref` like `late_delivery_v3#2.1`, embedded with BAAI/bge-small-en-v1.5 (384 dims) via **fastembed** (ONNX) and stored in `policy_documents` / `policy_chunks` (RLS, HNSW cosine index). Retrieval filters by effective date on the *order* date and by scope, keeps only the most specific scope per topic (location > brand > org), reports conflicts and "missing" explicitly, then ranks by cosine similarity. Every citation is marked untrusted. Tests use a deterministic hashing embedder (no download); `make seed` uses the real model (`--hash-embeddings` for offline).
- Why fastembed over sentence-transformers (the spec's name): same model and dimensions without PyTorch (~100 MB vs ~1 GB, much lower RAM); the dev machine already had a test run killed for low memory. Human chose it.
- Observed with the real model: similarity doesn't understand numbers ("over an hour late" ranked the "under 20 minutes" section first; the right document and version were still chosen). Callers take the top few sections, and minutes/amounts are always decided in code (`app/engine/resolver.py`, eligibility), never from similarity.
- Alternative rejected: one "latest" policy per topic regardless of order date (an order is judged by the policy in force when it was placed).

## 2026-10-24 · LLM provider factory: one client, our own backoff, JSON + one repair
- Decision: agents call models only through `app/llm/providers.LLMClient`. `get_chat_model(role, provider)` builds a LangChain chat model (Gemini/Groq/Ollama) with the model name from settings (`llm_<role>_model_<provider>`, `llm_ollama_model`); a missing key raises `MissingAPIKey` naming the env var. Provider SDK retries are off (`max_retries=0`): the client retries rate limits (429 / "rate limit" / RESOURCE_EXHAUSTED, detected generically) with exponential backoff, then switches to `LLM_FALLBACK_PROVIDER`; any other error is raised at once. A fallback with no key is skipped with a warning rather than breaking the primary.
- Structured output is prompt-based: a system message carries the Pydantic JSON schema, the reply is validated with `model_validate_json`, and on failure the validation errors (field + message, never input values) go back exactly once; a second failure raises `StructuredOutputError` for the engine to escalate.
- `RunBudget` counts logical calls (each invoke and each repair, cache hits included) and raises `BudgetExceeded` past `llm_max_calls_per_run` (8). Retries and fallbacks are counted separately and don't use up the limit. Tokens are counted from real calls only; cost is an integer-paise placeholder (0 on free tiers).
- Dev cache (`LLM_CACHE=1`): one JSON file per sha256 of (provider, model, messages, schema name) under `.llm_cache/`.
- Why: SDK retries plus ours would multiply wait time and hide 429s from the fallback logic; prompt-based JSON behaves the same on all three providers (small Ollama models included) and makes the repair message simple. Counting cache hits keeps routing identical with and without the cache, so evals don't change when the cache is on.
- Alternative rejected: `with_structured_output` (tool-calling/JSON-mode support and failure shapes differ per provider and model, and the repair turn is harder to build); LangChain `with_fallbacks` (falls back on any exception, not only rate limits, and doesn't count attempts).

## 2026-10-24 · Case + approval API (no-LLM path)
- Decision: `POST /cases` (customers, on their own orders only) stores the message in a ticket thread and runs a deterministic remedy chosen by the vertical pack's `remedies` map (late-delivery tiers, refund of missing items, voucher; unmapped categories escalate). The proposal goes through the same `create_proposal` + `auto_decide` path the LLM pipeline will use. `GET /approvals` lists undecided proposals in the caller's scope with the code checks; `POST /approvals/{proposal_id}/decision` records the decision and queues an approved refund as a background task; `POST /approvals/{proposal_id}/reconcile` queues a by-key reconcile (202). `GET /cases/{id}` shows only verified states: "confirmed" needs a provider-confirmed success; a timeout is "processing".
- The request session uses `Depends(..., scope="function")`: it commits as soon as the endpoint returns, before the response and before background tasks. Found by test: with the default request scope, the background refund ran before the decision was committed and saw no approval.
- Why: the money call never runs inside a request transaction (hard rule 5), and the customer is never told more than the provider confirmed (hard rule 7).
- Alternative rejected: executing the refund inline in the decision request (provider call inside an open transaction; slow request; a client retry could race the executor).
- After safety review: auto-approved refunds are queued too (none exist today; refunds are never auto-approved); missing-items refunds are capped by the percent limit; a refund approved but stuck (expired with no execution, or quarantined) is shown as "needs a check by our team", not "being processed"; non-refund remedies say "we will confirm once it is ready" (no executor yet); one open case per customer+order (a retry returns it). Known gap: a crash between committing the decision and running the in-process background task leaves an approved proposal with no execution. The key is stable, so retrying is safe; story E4.5 adds a sweeper.

## 2026-10-24 · Refund execution: lock, reserve, call outside, reconcile by key
- Decision: `execute_refund` follows PROJECT.md section 10 exactly. A short transaction locks the order row (`SELECT … FOR UPDATE`), re-checks the approval (`check_usable`) and eligibility against the refundable balance (captured payments − refunds reserved/submitted/succeeded/unknown/pending), then inserts the execution and the `reserved` ledger row under `P-<proposal_id>:refund:1` and commits. The connector call happens with no transaction open. The outcome is written in a second short transaction; a timeout is stored as `unknown`, never as success. Re-running for an existing execution never mints a key: it asks the provider by key first and re-sends with the same key only if the provider has no record (timeout before accept) or was temporarily unavailable. Amounts come from the hashed params, never a separate column.
- Eligibility is pure: `Action.validate(ctx, inp, facts)` gets a `Facts` object (effective settings, order total, refundable balance) built by the engine. This extends the spec's `validate(ctx, inp)` so actions stay deterministic and unit-testable with no DB.
- Decisions (`decide`): staff only, in scope (otherwise "not found"); eligibility re-checked when approving; refunds above `refund_without_escalation_paise` need an hq_owner; expiry from `approval_expiry_minutes`; a second decision → `AlreadyDecided`. `auto_decide` never approves refunds; vouchers up to `voucher_auto_approve_max_paise`.
- Why: the lock serialises reservations per order (two refunds that fit alone can't both pass), the DB constraints from 0009 back every step, and the same-key rule makes retries and crashes safe.
- Alternative rejected: calling the provider inside the reservation transaction (holds locks across the network; a crash leaves no record of the attempt).
- After safety review: resuming an existing execution first asks the provider by key. If the provider has it, it's recorded even if the approval has since expired (money already moved). If the lookup itself is unavailable, nothing is sent (reconcile later). Only if the provider has no record is a send allowed, and then the approval must still be usable. Otherwise the refund is quarantined: ledger `pending_reconciliation` (still holds the balance), execution `unknown`, nothing sent. "No record yet" is not proof that an earlier in-flight request won't land, so money is never freed automatically (a second refund could otherwise double-pay); a late success is still recorded. Releasing a quarantined refund is an operator action after a window longer than the provider's request lifetime (not automated in v1). Outcome writes only move forward (stale answers can't overwrite newer states) and never erase a provider reference; events are emitted only by the write that changed state. `decide` checks scope before anything else (all earlier failures look like "not found"), refuses a proposal whose hash isn't intact, and a proposal with no order is hq-only by design. Audit redaction matches key fragments case-insensitively and covers free-text notes.

## 2026-10-24 · Engine least privilege, and the Neon owner bypasses RLS
- Finding: Neon's `neondb_owner` has `rolbypassrls = true` (via `neon_superuser`). `FORCE ROW LEVEL SECURITY` does not constrain it. Moving the dev reseed to the owner role made one tenant's reseed delete every tenant's history in the test database (caught by tests before any merge; the main database was last reseeded as the app role).
- Decision: every statement run as the owner (reseed, test cleanup) filters on `tenant_id` explicitly, and a test proves reseeding tenant A leaves tenant B unchanged. Runtime code never uses the owner.
- Decision (migration 0009, after the E2.3a safety review): the app role can't delete engine rows; proposals, approvals and verifications are insert+read only; executions and refund_operations may only change status columns; audit_events append-only, and the migration fails if the app role is missing. Executions must reference an approved approval of the same proposal (composite FK including `decision`), one per proposal; refund reservations must match their proposal's amount and order (trigger), one per proposal; `amount_paise` must equal the param it came from (check); approval expiry capped at 7 days; a proposal's run must belong to its case; `create_proposal` refuses order/customer/case ids that don't belong to the case.
- Why: these are exactly the invariants the executor (E2.3b) relies on; making them structural means a bug or a race can't violate them.
- Alternative considered: a separate NOBYPASSRLS maintenance role for reseeds (RLS would protect the reseed too). Deferred: needs another role and URL in `.env`; explicit filters plus the cross-tenant test cover the dev-only path.
- Accepted risk (pending the human's decision): with explicit filters, a forgotten `WHERE tenant_id = ...` on an owner-run statement is not caught by RLS. The re-review found one such miss (`load_refs`, fixed; composite FKs would have rejected the cross-tenant ids, so it failed closed). Mitigations: owner engine used only by `scripts/seed.py`, `simulator/load.py` and test cleanup; two tests cover it (cross-tenant reseed counts, colliding slugs). The maintenance role remains the recommended hardening.

## 2026-10-24 · Proposals, approvals and the refund ledger are enforced by the database
- Decision: `action_proposals` are immutable (UPDATE rejected by trigger) and unique on `(tenant_id, id, payload_hash)`; `approvals` reference that triple (so an approval can only exist for the exact hash) and are unique per proposal (two managers can't both decide); a human approval needs `decided_by`, an auto one must not have it, and `expires_at > decided_at`. `executions` and `refund_operations` have unique idempotency keys per tenant; refund amounts are `bigint > 0`. `audit_events` is append-only for the app role (no UPDATE/DELETE/TRUNCATE). The payload hash is sha256 of canonical JSON of `{action, case_id, params}`, floats refused; params are validated in JSON mode against the action's strict `Input` (`extra="forbid"`, ints stay ints).
- Connectors are chosen per tenant by settings (`payment_connector`, `messaging_connector`, `orders_connector`), always addressed with `merchant_id_for(ctx.tenant_id)`; they translate provider exceptions into outcomes (`unknown` after a timeout, `unavailable` for transient errors) and never decide retries.
- Reseeding history (dev only) clears engine tables before commerce tables; audit rows stay.
- Why: the executor (E2.3b) will re-check all of this in code, but the database is the last line of defence against a bug, a race between two approvers, or a replayed approval.
- Alternative rejected: storing approval state on the proposal row (mutable proposal, approval not bound to a hash).

## 2026-10-23 · Mocks: in-process fakes with one idempotency core
- Decision: `mocks/` holds in-process fakes (payment, messaging, POS, delivery app) shared through a process-wide registry. Payment and messaging share `IdempotentMock`: one stored operation per (merchant, idempotency key); same key + same canonical-JSON payload hash → the stored operation (never re-applied, even after a decline); same key + other payload → `IdempotencyConflict` (HTTP 409); `get_by_key` for reconciliation is never subject to chaos. Seeded chaos: timeout before accept (nothing applied), accept-then-timeout (applied, caller can't tell), decline, processing-then-settle, delay. `/admin/chaos` (hq_owner) is only mounted when `APP_ENV` is not prod.
- Why: fast, deterministic contract and chaos tests with no extra processes (the dev machine has little headroom); keys scoped per merchant mirror real providers, so two tenants can never collide.
- Alternative rejected: standalone FastAPI mock services (extra processes and ports for the same contract); random unseeded chaos (flaky tests).
- After safety review: chaos is per merchant (`merchant_id_for(tenant_id)`), so an hq_owner only affects their own tenant; `/admin` mounts only for `APP_ENV` in {dev, test} (allow-list; unknown env names fail settings validation). Each chaos outcome comes from `Random(seed:merchant:key:attempt)`, so seeded runs reproduce regardless of thread order or other tenants' traffic. Calls return snapshots taken under the lock. Failure taxonomy for the executor: `ProviderTimeout` = unknown → reconcile by key, then retry with the same key; `ProviderUnavailable` (5xx/429 before accept) = nothing applied → retry with the same key; a `failed` operation (decline) is final for that key → a new attempt needs a new approval and a new attempt-scoped key, never a silently minted one.

## 2026-10-23 · Simulator: config-driven, fixed calendar, replace-on-reseed
- Decision: volumes, planted problems (late / missing_item / wrong_item / repeat_drop with location, hour and weekday filters) and messy-data rates live in each tenant's `simulation:` block; the generic simulator reads them plus the vertical pack (`fulfilment_kinds`). The window ends on a configured `end_date`, not today. Ids are uuid5 of the tenant + row number; reseeding deletes and reinserts the tenant's commerce rows in one transaction. The loader now prunes only config tables (`CONFIG_MODELS`).
- Why: no tenant names in code (hard rule 2); same seed → byte-identical data on any day; delete+insert is simpler and faster than upserting ~80k rows. Measured: full seed of both tenants 47 s on Neon.
- Rate tolerance: planted rates must match within ±1 point, or 3 standard errors for narrow slices (e.g. one outlet's weekday mornings, ~300 orders, where ±1 point is below sampling noise). Averaged over 6 seeds every planted rate is on target (bias check).
- Alternative rejected: hard-coding the spec's planted problems per tenant in Python; dates relative to `now()` (non-reproducible).

## 2026-10-23 · Demo auth: thin token, scope from the DB, fail closed
- Decision: `POST /auth/login {tenant, email, password}` with one demo password for seeded users (`DEMO_AUTH` can switch it off). The HS256 JWT holds only `tid` + `sub` + `exp` (secret must be ≥ 32 bytes). Every request re-reads role and location/brand scope from the DB inside the token's tenant session. Out-of-scope and other-tenant records both return 404; a customer on a staff route gets 403 (the route exists for everyone, the record question doesn't arise).

## 2026-10-25 · An approved refund the executor refuses is recorded as a failed execution
- Decision: when `execute_refund` refuses an approved proposal for a reason re-running won't fix (`not_eligible`, e.g. another approved refund used the balance first, or `no_captured_payment`), it writes an `executions` row with status `failed`, error `refused: <reason>`, the stable key, and no ledger row (nothing held, nothing sent), plus a `refund.refused` audit event and a `refund.failed` domain event. If another worker already created the execution, theirs stands. The refusal is recorded under the same order lock a reservation takes (`order_facts(..., lock=True)`), after re-checking eligibility and the captured payment there: if the refund fits again by then (a competing refund failed and freed the balance), nothing is recorded and the executor retries the reservation once. So a refusal and a reservation for the same order can never interleave. Found by the E4.3 chaos suite.
- Why: before, the refusal was only a log line: no audit trail, the proposal left the approval queue, and the customer was told "being processed" until the approval expired (hard rule 7). Now the case shows "escalated" at once and staff can see why.
- Alternative rejected: leave it unrecorded and let a sweeper retry it later (the balance could free up if the other refund fails, but acting on a stale decision is a new decision a human should make: re-propose instead).

## 2026-10-25 - `make eval` refuses to reseed the dotenv's default database

- Why: the eval reseeds, which deletes cases. A run from a worktree reusing the main `.env` wiped the demo database's cases.
- Rejected: an environment-variable allow-list (more setup, easy to forget) and a "name must contain test" rule (wrong for legitimate scratch names).

## 2026-10-25 - One execution path for approved proposals (E4 integration)
- Decision: `lifecycle.execute_approved` is the only function that runs an approved proposal (any action in `dispatch.EXECUTORS`: refund, free_item_voucher). `execute_and_verify` = it + `verify_executed`; `reconcile_and_verify` is the matching reconcile. `dispatch.run_approved` / `dispatch.reconcile` are thin calls into them (lazy import: lifecycle builds on dispatch's executor table). Callers: the graph execute/verify nodes, the staff decision route (`routes_approvals._after_decision` resumes the paused thread, and only on "skipped" calls `run_execution`), auto-approval on case open (`run_execution`), the baseline graph after `propose`, the sweeper (resumes a paused thread first, else the same entry) and `/reconcile`. A staff approval that both resumes the graph and fires the fallback sends one provider operation: executors serialise on the proposal and share one stable key.
- Verification: refunds are verified by re-reading the payment provider by key (status, amount, reference); the case is resolved only on success AND a verified verdict. Vouchers are verified by the provider-confirmed execution status only: the voucher executor always asks the provider by key before re-sending, and there is no amount/reference ledger to compare, so a second read adds nothing. `verify_executed` emits `case.verified` for them so the customer update fires; a timeout stays "processing".
- Guards kept: ids-only checkpoint state, tenant/case ownership on resume, prune (the sweeper now calls `prune_finished` and `events.publish_pending`), the late-run skip in `store_proposal` (the graph ends there, the run is marked failed), forward-only statuses, and `lifecycle.escalate` no longer overwrites a case a person already resolved/closed/escalated.
- Why: two parallel paths (graph execute vs. dispatch) risked divergent rules (verification, escalation, events) and double sends if one drifted from the other.
- Alternative rejected: making `dispatch.run_approved` the owner (it would have to import lifecycle for events/escalation, and the graph nodes would need a second set of status strings).

## 2026-10-26 - DPDP posture and data minimisation in LLM prompts (E3.4)
- Decision:

  - Prompts carry only what a decision needs. The read tools return a customer reference, order lines, fulfilment times, payments and previous case categories, never a name, email, phone or address. The customer's own message has emails and phone numbers masked (`[email]`, `[phone]`) in `fence_customer`, so every prompt gets the masked text.

## 2026-10-26 - Growth module (E8): own campaign tables, dual approval, intention-to-treat verdict
- Decision: migration 0015 adds `signals`, `campaigns`, `campaign_members`, `campaign_approvals`, `playbook_entries` (tenant_id + forced RLS). A campaign is an ActionProposal-style record with its own `payload_hash` (signal, location, params and the exact treatment/holdout ids) and `expires_at`; `action_proposals` is not reused because its rows hang off a support case. Approvals are one row per (campaign, user), never edited; the campaign is `approved` when two different staff users, at least one `hq_owner`, hold unexpired approvals for the stored hash. The app role cannot update `params`/`payload_hash`/members' arm or delete any growth row (column grants), and the executor re-checks hash, expiry and the dual rule before sending.
- Detection: repeat rate per location (an order is a repeat if the customer ordered there in the prior 28 days), last 21 days vs the 28 days before, stored as basis points. Flag only if the drop is >= 5 points, both windows have >= 30 orders and a one-sided two-proportion z >= 1.64 (so a quiet outlet does not raise a false alarm). One signal per (location, metric, window end): re-runs are no-ops. Tested via the simulator's `repeat_drop` config, never a tenant name.
- Diagnosis: code gathers read-only evidence (ticket categories, rates); a deterministic template summarises it. An LLM may rewrite the summary only in `run_nightly` (three phases, no transaction open during the call) and never in a request; it sees the evidence JSON and no tools, and any failure falls back to the template.
- Audience and sends: lapsed = ordered at the flagged location, none in the 28 days before the window ended; needs a phone, WhatsApp marketing consent (no row = no consent), no campaign in the last 30 days, one customer per phone. Split = rank by sha256(signal id : customer id), first `growth_holdout_percent` held out (>= 1 held out, >= 1 treated). Budget = offer x treatment size, capped by the new `growth_campaign_budget_paise` setting. One send per (campaign, customer) under key `C-<campaign>:<customer>:send:1`, after both approvals, outside any transaction, forward-only member status; re-runs and racing workers send the same keys, so the mock outbox holds one message each. Holdout members are never contacted (also a DB check).
- Verdict: intention-to-treat (every assigned member counts, even a failed send), orders at the location inside [sent_at, sent_at + window). `worked`/`did_not_work` only with >= 20 per arm and |z| >= 1.96, else `inconclusive` with a note saying which. One playbook row per campaign. Simulator hook `simulator/growth.py` plants post-campaign orders per arm.
- Simplest-safe choices: no `metric_snapshots` table (the signal row holds the windows and counts); the proposal TTL is 48 h and each approval's is 24 h (constants, not settings); campaign `expired` is derived from `expires_at` at read time (no sweeper yet); the API is staff-only under `/growth`, gated by the tenant `growth` flag (404 when off); no web UI.
- Alternative rejected: reusing `action_proposals`/`approvals` (case-bound, single approver) and sending from the request (a transaction would be open during the provider call).

## 2026-10-28 - Fair vouchers and fair-use as a warning (S7.8, S7.11)
- Decision: a voucher is `min(voucher_max_paise, voucher_auto_approve_max_paise, voucher_percent of the order total)`, rounded down to whole rupees; under Rs 10 the case escalates instead of proposing. `voucher_percent` is a new vertical-pack `limit` setting (default 100, lower only). The voucher action also rejects a value above the order total and shows `order_total_paise` in the approval checks. The approvals page renders `fair_use_ok=false` as an amber "Repeat claimant ... a person must decide" warning, not a red failure.
- Why: a flat Rs 150 voucher on a Rs 149 order paid out more than the customer spent. The agent path shares `decide_remedy` as its ceiling, so it picks up the same value. - Floor: the Rs 10 minimum is kept on purpose (a smaller voucher is noise); such cases go to a person. Packs stored before `voucher_percent` existed read as 100, and a voucher with no readable order total fails validation (closed).
- Alternative rejected: item-line totals for item-specific categories (no reliable data link yet); a fixed minimum percent; hiding the fair-use check altogether.

## 2026-10-28 - Re-run the AI on an AI-failure escalation (S7.4, S7.7)
